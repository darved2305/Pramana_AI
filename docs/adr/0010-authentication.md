# 0010: Console sign-in with server-side sessions; participants keep signed links

**Status:** accepted

**Context.** The console (Next.js 16, `apps/web`) reaches the core only through same-origin
rewrites (`/api/core/*` in `next.config.ts`), so the browser sees one origin. Three kinds of
caller exist: staff who run investigations (**operator**), staff who authorise repairs
(**approver**), and participants who answer from a join link. Until now nothing was
authenticated, and the approver's identity was a free-text field.

**Options compared.**

| | Server-side session, httpOnly cookie (chosen) | Bearer JWT in browser storage | Hosted identity (Auth0, Clerk) |
|---|---|---|---|
| Token theft by XSS | Cookie is `HttpOnly`: page scripts cannot read it | Any XSS can read `localStorage` and replay the token elsewhere | Same as the cookie option when its SDK uses cookies |
| Revocation | Delete the row; sign-out ends the session everywhere at once | Needs a deny list until expiry | Provider-side |
| CSRF | Must be handled (below) | Not applicable | Must be handled |
| Works through the Next rewrite | Yes: same origin, the cookie is sent automatically, `Set-Cookie` passes through | Yes | Needs callback routes and provider configuration |
| New dependencies | None: `hashlib.scrypt`, `secrets`, SQLAlchemy | A JWT library | An SDK and an external account; adds a network dependency to the demo |

The OWASP Session Management Cheat Sheet recommends opaque, random session ids of at least 64
bits of entropy, stored server-side, in cookies with `HttpOnly`, `Secure` (on HTTPS) and
`SameSite`. FastAPI's own security tutorial uses bearer JWTs, but its examples target API
clients, not a browser app on the same origin.

**Decision.**
1. **Staff sign in** with email and password (`POST /v1/auth/login`). The core creates a
   256-bit random session id (`secrets.token_urlsafe(32)`), stores only its SHA-256 in
   `sessions`, and sets `pramana_session` as `HttpOnly; SameSite=Lax; Path=/`, plus `Secure`
   in `PRAMANA_MODE=demo` (`SESSION_COOKIE_SECURE` overrides). Sessions last 12 hours
   (`SESSION_TTL_S`). Sign-out deletes the row; a replayed cookie then fails.
2. **Passwords** are hashed with the standard library's scrypt (`n=2^14, r=8, p=1`, 16-byte
   salt), the OWASP Password Storage Cheat Sheet's scrypt minimum, with parameters stored per
   hash. Unknown emails are verified against a dummy hash so timing does not reveal whether an
   account exists, and every failure returns the same message. Five failures per email in five
   minutes return `429 AUTH_RATE_LIMITED` (per process).
3. **CSRF.** `SameSite=Lax` already stops cookies on cross-site `POST`. In addition, every
   unsafe request authenticated by the cookie must carry `X-Pramana-CSRF: 1`, and so must the
   sign-in request itself (blocking login CSRF). A cross-site page cannot add a custom header
   without a CORS preflight, and the core's CORS list contains only our origins. This is the
   OWASP CSRF Cheat Sheet's "custom request headers" defence.
4. **Roles.** `operator`: create investigations, manage the directory, request approvals,
   mint join links, reveal. `approver`: decide approvals. Either role may read investigations,
   the directory and evaluation reports. **The approval records the signed-in approver's id;
   an `approver_id` in the request body is ignored.** Unauthenticated calls get
   `401 AUTH_REQUIRED`; a missing role gets `403 ROLE_FORBIDDEN`.
5. **Participants** never sign in. The join link carries the Ed25519 participant token the core
   already mints for the simulator. Sent as `Authorization: Bearer`, the core verifies it with
   the public half of its own signing key and allows only that person's own actions in that
   investigation: reading it, answering their own questions (typed or spoken), fetching their
   question audio, collecting their capability and reporting their intervention. Another
   participant's token, or one for another investigation, gets `403 PARTICIPANT_FORBIDDEN`.
   The audio and voice-answer checks run before any paid Gnani call.
6. **Automation** (`scripts/run_text_investigation.py`, bots, the benchmark) sends
   `X-Automation-Key` (`CORE_AUTOMATION_KEY`, generated by `scripts/dev_env.py`), which acts as
   operator and approver. A wrong key is rejected (`401 AUTH_INVALID_KEY`), never ignored.
7. **Tests.** Sign-in is enforced unless `PRAMANA_MODE=test` (override with `AUTH_REQUIRED`).
   The engine and runtime suites test behaviour; `test_auth*.py`, `test_directory.py` and
   `test_evaluation.py` run with it enforced.
8. **Users** are created by `uv run python -m pramana_core.auth.bootstrap --email ... --name ...
   --roles operator,approver`, with the password from `PRAMANA_NEW_USER_PASSWORD` or a prompt,
   never from the command line. No credentials are committed.

**Consequences and limits.**
- A participant token currently reads the whole investigation state, including other
  participants' answers. A participant-scoped view is a follow-up.
- The `/v1/voice/*` test routes are not yet behind a role; they spend credits and should be.
- The login throttle is per process, which matches the single-process core (ADR 0003).
- There is no password reset or self-registration; an operator creates accounts.
