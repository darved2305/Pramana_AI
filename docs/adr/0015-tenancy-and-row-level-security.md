# 0015: Tenancy: organizations, memberships, `org_id` everywhere, row-level security

**Status:** proposed

**Amends:** 0003 (the event log gains `org_id`; event idempotency keys become unique per
investigation) and 0010 (roles move from the user to a membership in an organization).

**Context.** PRODUCTION.md §1.4 and §4. Today there is one building and no organizations:
`users`, `investigations` and `directory_participants` carry no tenant, and `campus_block_c` is
the default site in the API, the readiness check and the console. Two campuses cannot share the
service, and a missing `WHERE` clause in any query would show one customer's data to another.

**Options compared.**

| Option | For | Against |
|---|---|---|
| Silo: a database (or schema) per organization | Strongest isolation; easy per-tenant restore | Migrations run N times; connection pools per tenant; heavy for small campuses |
| **Pool: shared tables, `org_id` on every row, RLS as a second lock** | One schema and one migration path; cheap per tenant; RLS fails closed | Every query and index must carry `org_id`; RLS needs a correct per-transaction context |
| Pool without RLS | Simplest | One forgotten filter leaks data; nothing catches it at runtime |

**Decision.**
- Pool model (AWS SaaS terminology). New tables `organizations`, `memberships`, `sites`,
  `site_models`; `org_id uuid not null` on every tenant table, leading every composite index.
- UUIDv7 primary keys generated by the application, exposed as type-prefixed public ids
  (`org_`, `site_`, `inv_`, ...), replacing today's 48-bit `prefix_` plus 12 hex characters.
- `ENABLE` and `FORCE ROW LEVEL SECURITY` on every tenant table, with one policy:
  `org_id = nullif(current_setting('app.org_id', true), '')::uuid` in both `USING` and
  `WITH CHECK`. Without a context the policy matches nothing.
- `Database.transaction()` sets the context with `set_config('app.org_id', :org, true)`
  (transaction-local, safe under pooling) from the request's organization.
- The application connects as a non-superuser `pramana_app` role. Superusers and `BYPASSRLS`
  roles skip RLS even with `FORCE`, and the local cluster's `pramana` role is a superuser
  (`scripts/dev_db.py` runs `initdb -U pramana`), so `pramana` runs migrations only.
- The API's membership check is the first lock and RLS the second. A resource in another
  organization answers `404`, never `403`, so existence does not leak (OR-03).
- Platform tables with no tenant (`users`, `user_identities`, `sessions`, `auth_flows`) are not
  under RLS; they are reached only through the authenticated principal.

**Consequences.** Every repository method takes an organization context, and background work
must set one per job. Cross-tenant admin work needs an explicit, audited break-glass path. The
`campus_block_c` pack becomes the stored sandbox model of each organization (`mode='sandbox'`).
`org_id` everywhere keeps sharding by organization possible later without a rewrite (§3.11).

**Tests.**
- With `pramana_app` and no `app.org_id`, every tenant table returns zero rows.
- Inserting or updating a row of organization A with the context of B fails `WITH CHECK`.
- The tenant-leak generator: for every route in `services/core/openapi.json`, a member of B
  calling A's resources gets `404` or `403` and never data; a new route without a tenant case
  fails the test.
- The existing investigation, replay, reveal, approval and voice suites pass under the
  organization-scoped routes.
