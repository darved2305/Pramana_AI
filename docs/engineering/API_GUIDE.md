# API guide for frontend integration

Two services:
- **core** on `http://127.0.0.1:8000`: investigations, voice and approvals.
- **simulator** on `http://127.0.0.1:8100`: what each participant "sees".

The browser talks to both: to the simulator only with a participant's own token, and to the
core for everything else. The Gnani key never reaches the browser.

**Specifications:**
- `services/core/openapi.json`: every core route and schema, regenerated by
  `make openapi` and checked in CI.
- `packages/contracts/schema/pramana.schema.json`: the JSON Schema bundle for the contract
  models, for generating TypeScript types with `json-schema-to-typescript`.

**Run locally:** `make db-up && make migrate`, then `make sim`, then `make core`. CORS allows
`http://localhost:3000` by default (`CORS_ORIGINS` / `SIM_CORS_ORIGINS`).

**Errors** always look like this. Branch on `code`, not on the message text:

```json
{"error": {"code": "QUESTION_NOT_PENDING", "message": "...", "request_id": "..."}}
```

Every response carries `X-Request-ID`. Send your own to correlate logs.

## 0. Sign-in and roles (docs/adr/0010-authentication.md)

Sign-in is enforced unless `PRAMANA_MODE=test`. Three kinds of caller:

| Caller | How | May |
|---|---|---|
| Operator (staff) | session cookie | create investigations, manage the directory, request approvals, mint join links, reveal |
| Approver (staff) | session cookie | approve or deny; the approval records **their** id (any `approver_id` in the body is ignored) |
| Participant | `Authorization: Bearer <join token>` | read **their part** of their investigation (their entry, answers, question, approvals and the status; no hypotheses, plan, other people's answers or event log); answer, hear and act on **their own** questions and approvals |
| Script or bot | `X-Automation-Key: <CORE_AUTOMATION_KEY>` | operator and approver |

```http
POST /v1/auth/login   {"email", "password"}   (header X-Pramana-CSRF: 1)
-> 200 AuthSession, Set-Cookie: pramana_session=...; HttpOnly; SameSite=Lax
GET  /v1/auth/session -> AuthSession, or 401 AUTH_REQUIRED
POST /v1/auth/logout  -> 204 (deletes the session server-side)
```

Every `POST`, `PATCH` and `DELETE` sent with the cookie must include `X-Pramana-CSRF: 1`
(`403 CSRF_HEADER_MISSING` otherwise). Error codes: `401 AUTH_REQUIRED`,
`401 AUTH_INVALID_CREDENTIALS`, `401 AUTH_INVALID_TOKEN`, `401 AUTH_INVALID_KEY`,
`403 ROLE_FORBIDDEN`, `403 PARTICIPANT_FORBIDDEN`, `429 AUTH_RATE_LIMITED`.
Create users with `uv run python -m pramana_core.auth.bootstrap --email ... --name ...
--roles operator,approver` (password from `PRAMANA_NEW_USER_PASSWORD` or a prompt).

## 1. Console: create and watch an investigation

### Reproducible scenarios

Staff can fetch the built-in scenarios with `GET /v1/investigations/presets`. Each result has an
`id` (`S2` or `S7`), a title and description, and a complete `request` body accepted by
`POST /v1/investigations`. Use that request as the starting point when creating the scenario.
S2 demonstrates conflicting Wi-Fi reports and their reconciliation. S7 demonstrates a restricted
location check and a presence challenge.

```http
POST /v1/investigations
{
  "pack_id": "campus_block_c",
  "participants": [
    {"id": "p_riya", "display_name": "Riya", "roles": ["student"], "skill": "lay",
     "location_id": "F3_R304",
     "languages": {"stt_candidates": ["hi-IN", "en-IN"], "template_language": "hi-en",
                   "codemix": true}},
    {"id": "p_mahesh", "display_name": "Mahesh", "roles": ["guard"], "skill": "access",
     "location_id": "GUARD_DESK",
     "languages": {"stt_candidates": ["mr-IN", "hi-IN"], "template_language": "mr"}},
    {"id": "p_imran", "display_name": "Imran", "roles": ["electrician"],
     "skill": "technician", "location_id": "MAINT_ROOM",
     "languages": {"stt_candidates": ["hi-IN"], "template_language": "hi"}}
  ],
  "report": {"text": "Floor 3 pe WiFi nahi chal raha", "reporter_id": "p_riya"},
  "scenario": {"seed": 19, "fault": "random"}
}
-> 201 InvestigationState
```

`fault` is `"random"` (sealed) or `{"faults": [{"component_id": "CB_C2_7", "mode": "tripped"}]}`.
The core never stores the fault; only the simulator does.

### Listing investigations

`GET /v1/investigations?status=decided&status=verified&q=wifi&limit=25&offset=0` returns
`InvestigationPage {items, total, limit, offset}`, newest first. `status` may repeat; `q` matches
the report text or the id (case-insensitive; `%` and `_` are literal). Each item has `status`,
`report_text`, `reporter_id`, `participant_count` and, once concluded, `decision_class` and
`decision_probability`.

### `InvestigationState`: what to render

| Field | Shows |
|---|---|
| `status` | `investigating`, `decided`, `abstained`, `awaiting_approval`, `acting`, `verifying`, `verified`, `not_verified` or `closed` |
| `sealed_commitment` | The SHA-256 hash published at the start (the "sealed fault" badge) |
| `belief.hypotheses[]` | Every possible cause, with `probability`, sorted descending (the bars) |
| `belief.decisions[]` | What to do, with probabilities (the decision bar) |
| `belief.hypothesis_entropy_bits`, `decision_entropy_bits` | The uncertainty meter |
| `belief.open_world_probability` | The "unknown cause" row; always show it |
| `belief.repair` | After a repair: `fixed_probability` and the number of post-repair observations |
| `plan` | The **persisted** trace that produced the current question or conclusion |
| `plan.reason` | A one-paragraph explanation generated from the numbers, not by an LLM |
| `plan.candidates[]` | "Why this question?": `eig_decision_bits`, `cost_s`, `score`, `net_value_min`, and `outcomes[]`, the predicted result of each possible answer |
| `plan.infeasible[]` | Observations nobody available can make, and why ("needs role electrician") |
| `pending_question` | The question waiting for an answer: who, what and where, plus `text` in their language. `kind` is `probe`, `confirm` or `challenge`. A `challenge` has `presence_token_id`, an empty `outcomes` list, and asks the person to read a site label. |
| `observations[]` | The evidence ledger: outcome, hedge, directness, modality, transcript and `state` (`committed`, `discarded` or `superseded`) |
| `approvals[]` | Approval cards: action, target, risk, reversibility, rationale and status |
| `ground_truth` | After the reveal: the fault, `commitment_verified`, and whether the decision was `correct` |

The console's presence and reconciliation panels are folded from the event log. A location check
shows the challenged person, location and status (`Asked`, `Passed` or `Not confirmed`). Location-
bound observations show `Presence check asked · reduced weight` while pending,
`Presence verified` after a pass, or `Presence not confirmed · reduced
weight` after failure. A failed check is explained neutrally and the planner can ask another
person. The console never receives the expected label characters.

For `ContradictionExplained`, the console pairs the referenced observations, ranks the language-
independent explanation families by posterior mass, and renders reviewed English templates from
the event codes and pack contexts. The tie-break question appears while pending; its recorded
outcome appears after `ContradictionResolved`. Replay shows the same event-backed details at the
point they occurred. Existing investigations load prior events on open, then follow server-sent
events with polling as the fallback.

### Live updates

Poll `GET /v1/investigations/{id}/events?after_seq=N`. It returns new events in order, and
`seq` only ever increases, so keep the last one you have seen. Main types:
- `InvestigationCreated`, `ReportReceived`
- `ObservationRecorded`, `BeliefUpdated`, `PlanComputed`, `QuestionAsked`
- `DecisionReached`, `Abstained`
- `ApprovalRequested`, `ApprovalDecided`, `CapabilityIssued`, `InterventionReported`
- `VerificationResult`, `Reopened`, `GroundTruthRevealed`
- `ObservationConfirmed` (`agreed`: true, false, or null if the confirmation was unclear)
- `ChallengeIssued` and `ChallengeResult` (participant, location, token id on issue, cost, and pass/fail/withdrawn reason; never the expected characters)
- `ContradictionExplained` and `ContradictionResolved` (language-independent explanation codes, posterior masses, supported access-point contexts, the tie-break action, and its answer)

Re-fetch the state after any event, or fold `BeliefUpdated` and `PlanComputed` payloads
directly.

### Reveal

`POST /v1/investigations/{id}/reveal` returns the state with `ground_truth`. It is allowed only
after a decision, an abstention or a verification result, and it closes the scenario.

## 2. Participant page

1. `POST /v1/investigations/{id}/participants/{pid}/token` returns
   `{token, scenario_id, sim_url}`.
2. Surroundings: `GET {sim_url}/sim/v1/scenarios/{scenario_id}/view` with
   `Authorization: Bearer {token}`. It returns `{location_label, items: [{label, value}],
   reachable_locations}`. Show a "SIMULATION" label.
3. When `pending_question.action.participant_id == pid`, show `pending_question.text`. If
   `requires_move` is true, first `POST {sim_url}/sim/v1/scenarios/{sid}/move {"to": location_id}`.
Send the same token as `Authorization: Bearer {token}` on the core calls below.

For a `challenge`, move first and then read the rendered label card from the participant's
simulator view. `GET {sim_url}/sim/v1/scenarios/{sid}/view` includes `presence_tokens` only when
that participant is physically at the token's location. Submit the spoken or typed letters and
digits through the same text or voice answer route as other questions. The response is a
`ChallengeAnswerResult` with `passed`, neutral `message` and updated `state`; it contains no
recognised code or observation. A failed check leaves that person's evidence at the documented
unverified-presence weight and the planner can ask someone else. A challenge is not reissued to
the same person at the same location. The participant page uses a labeled, uppercase monospace
field with a text keyboard for short codes. The simulator decides whether a label is visible; the
page does not synthesize or cache it. Failure text follows the participant's selected language.

The simulator also exposes `POST /sim/v1/scenarios/{sid}/presence/verify` for core-to-simulator
use. It requires `X-Operator-Key` and accepts `{participant_id, token_id, answer}`. Its only result
is `{passed: true|false}`. Do not call it from a participant page. Token characters are generated
per scenario and are never returned by this endpoint or written into events.

4. Answer by **text**: `POST /v1/investigations/{id}/answers {question_id, participant_id, text}`.
   Or by **tap**: send `outcome` (one of `pending_question.outcomes`) instead of `text`.
5. Answer by **voice**: `GET /v1/investigations/{id}/questions/{qid}/audio` plays the question
   (WAV; cached, so replays cost nothing). Then `POST /v1/investigations/{id}/answers/voice`
   (multipart: `question_id`, `participant_id`, `audio`) returns `{stt, result}`.
   - `422 VOICE_EMPTY_TRANSCRIPT`: ask them to repeat (nothing was recorded).
   - `409 QUESTION_NOT_PENDING`: someone already answered.

The answer response includes `extraction`: what was understood (`outcome`, `hedge`,
`directness`, `injection_suspected`). Show it back to the participant ("I understood: off").
Challenge responses are the exception: they intentionally omit extraction details and recognised
characters.

### A whole call over one socket

`WS /v1/investigations/{id}/participants/{pid}/call` (protocol in `voice/call.py`): send
`{"type":"start","token":...,"play":true}`, receive `ringing`, send `{"type":"accept"}`, receive
`consent_request {text}` (and its audio), send `{"type":"consent","answer":"yes"|"no"|"later"}`.
After a yes, every question the engine addresses to this person runs as a turn on the same
socket (the per-question frames: `ready`, `tts_*`, PCM16 up, `commit`, `transcript`, `answer`),
and the call waits in `IDLE` for the next one. It ends with `call_end {reason}`.
Declining, saying "later", not answering the ring, or 20 s of silence takes the person out of the
investigation (`ConsentRecorded`, `ParticipantUnavailable`, `QuestionCancelled`); the engine asks
someone else.

## 3. Approval and repair (console and electrician)

| Step | Who | Call |
|---|---|---|
| Request | console, after `decided` | `POST /v1/investigations/{id}/approvals {action:"reset_breaker", target:"CB_C2_7", participant_id:"p_imran"}` |
| Decide | approver | `POST .../approvals/{aid}/decision {decision:"approve"\|"deny", approver_id}` |
| Collect | electrician page | `POST .../approvals/{aid}/capability?participant_id=p_imran` returns `{capability, expires_at, instructions}`. Issued once; expires after 5 minutes |
| Act | electrician page | `POST {sim_url}/sim/v1/scenarios/{sid}/act {action, target, capability}` with the participant token, standing at the panel |
| Report | electrician page | `POST /v1/investigations/{id}/interventions {approval_id, participant_id}`. Verification questions follow as normal pending questions |

The simulator's reply to `act` never says whether the repair fixed anything; that only shows
in what people observe afterwards.

## 4. Voice test page

Staff only: status and usage need a signed-in staff member; STT, TTS and the stream need the
operator role (scripts send `X-Automation-Key`).

| Route | Purpose |
|---|---|
| `GET /v1/voice/status` | Whether Gnani is configured |
| `GET /v1/voice/usage` | Today's spend (₹) and the limiter state |
| `POST /v1/voice/tts {text, language: "mr-IN"\|"hi-IN"\|"en-IN"\|"hi-en"}` | Speech as WAV; header `X-TTS-Wall-Ms` |
| `POST /v1/voice/stt` (multipart `audio`, `language_codes`, `codemix`) | Returns `SttResult` |
| `WS /v1/voice/stream` | Send `{"type":"start","language_code":["hi-IN","en-IN"]}`, then binary PCM16 at 16 kHz mono, then `{"type":"commit"}`. Receive `ready` (with `model_confirmed`), `speech_start`, `processing` and `transcript` |

Limits that can surface as errors:
- `429 VOICE_RATE_LIMITED_LOCAL` (per-minute cap)
- `429 VOICE_TOO_MANY_STREAMS` (16 concurrent)
- `429 VOICE_BUDGET_EXCEEDED` (daily ₹ cap)
- `503 VOICE_NOT_CONFIGURED`

## 5. Site layout for drawing the building

`GET /v1/packs` lists every pack (`id`, `version`, `title`, `locations`, `probes`); it is public.

`GET /v1/packs/campus_block_c` returns the locations (floor, kind, label, restricted), probes and
decision classes. It contains no simulator state.

## 6. Participant directory

People a site can call on, stored per pack. Operators edit it; any staff member can read it.
An investigation copies the participants it needs, so editing the directory never changes a
past investigation.

| Call | Result |
|---|---|
| `GET /v1/participants?pack_id=` | `DirectoryParticipant[]` (`pack_id`, `participant`, `created_at`, `updated_at`) |
| `POST /v1/participants?pack_id=campus_block_c` with a `ParticipantSpec` | `201`; `409 PARTICIPANT_EXISTS`; `422 UNKNOWN_LOCATION` / `UNKNOWN_PACK` |
| `GET /v1/participants/{pid}?pack_id=` | one entry, or `404` |
| `PATCH /v1/participants/{pid}?pack_id=` with any `ParticipantPatch` fields | the merged entry, re-validated as a whole |
| `DELETE /v1/participants/{pid}?pack_id=` | `204` |

## 7. Evaluation reports

`GET /v1/evaluation/reports` lists the runs under `eval/reports/*/summary.json`
(`EVAL_REPORTS_DIR`), newest first: `run_id`, `git_sha`, `seeds`, `policies`. `GET
/v1/evaluation/reports/{run_id}` returns `{run_id, modified_at, summary}` with the harness's
file as written, except that `NaN` and infinities become `null` so the response is valid JSON.
Nothing is computed by the core.
